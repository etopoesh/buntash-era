## 1. Назначение и рамки

«Долгий век» — командная ролевая историческая игра для 7-х классов
(школа 1576 «Праздники эпох»). Один ведущий и несколько родов-команд проходят
историю Русского государства с 1549 по 1682 год: от Собора примирения до отмены
местничества. Каждая команда играет боярский или дворянский род и управляет
тремя ресурсами: знатностью, рублями и крестьянами.

**Цель игрока:** набрать как можно больше знатности. При равенстве знатности
выше стоит род с большим числом крестьян, затем — с большим количеством денег.
(Новая система оценки итогов финального собора, ТЗ: порядок — знатность → крестьяне → рубли → имя.)

**Вне рамок проекта:** аккаунты и пароли, серверная игровая логика, защита от
подмены данных, античит, модерация, платежи, мобильное приложение.

**Особенности эксплуатации:** состояние партии общее для всех устройств и хранится
в Firebase Realtime Database; ведущий и рода работают одновременно с разных
устройств; события и постройки читаются из статических JSON-файлов.

## 2. Роли и режимы

| Роль | Вход | Что видит и может |
|---|---|---|
| Гость | Лендинг | «Начать игру», «вход для организатора» |
| Род | «Начать игру» → выбор своего рода из списка | Свой ход, ресурсы, историю, постройки, усадьбу |
| Ведущий | «вход для организатора» (мелкая ссылка на лендинге) | Все рода, темп, итоги, рассадку, торги, ворота соборов |

Роль и выбранный род хранятся только в памяти страницы. После перезагрузки
страницы нужно снова нажать «Начать игру» и выбрать род. Это осознанное
упрощение: общего логина нет, устройства команд не различаются.

Сословие рода задаётся ведущим при создании рода и хранится в `rod.estate`:
`boyare` (боярский) или `dvoryane` (дворянский). Сословие влияет на стартовую
знатность, бегство крестьян и часть эффектов выборов.

## 3. Архитектура

### 3.1 Файлы и порядок загрузки

`index.html` подключает скрипты строго по порядку (все с `defer`):

1. `firebase-init.js` — конфигурация Firebase, `stateRef`, `loadEvents()`, `loadBuildings()`;
2. `state.js` — модель состояния, все правила, транзакции, расчёты;
3. `view-rod.js` — экраны рода и построек;
4. `view-gm.js` — экраны ведущего;
5. `main.js` — `boot()`, подписка на базу и общий `render()`.

Порядок важен: `view-*.js` и `main.js` используют функции и константы из
`state.js`; менять порядок нельзя.

### 3.2 Поток данных

```
events.json ─┐
buildings.json ─┼─→ boot() ─→ state.events / state.buildings
                │
Firebase RTDB ──┴─→ stateRef.on('value') ─→ state ─→ render() ─→ #app
                                                    ↑
                    действия игрока/ведущего ───────┘
                    (dbSet / dbUpdate / dbTx / dbClaim, затем новая отрисовка)
```

- Состояние партии — один узел `buntash-state`.
- События и постройки **не хранятся в базе**: они всегда перечитываются из JSON
  при загрузке страницы. Поэтому правка контента не требует миграции базы.
- `render()` полностью перерисовывает `#app`; точечного DOM-обновления нет.
- Все записи идут по путям и транзакциям. Принцип: у каждого поля один автор,
  общие числа меняются транзакциями, а не перезаписью всего состояния.
- Ошибки записи показываются баннером `errorBanner()` (текст «Ошибка облака…»).

### 3.3 Подключение Firebase

`firebase-init.js`:

```js
databaseURL: 'https://buntash-era-default-rtdb.firebaseio.com'
stateRef = db.ref('buntash-state')
```

Правила безопасности базы в репозитории отсутствуют. Публичная запись открыта —
это приемлемо для школьной игры, но не для публичного интернета.

## 4. Модель данных

### 4.1 Корневое состояние `state` (`initialState()`)

| Поле | Тип | Назначение |
|---|---|---|
| `currentIndex` | number | Текущий ход в интерфейсе ведущего |
| `events` | array | Загруженные события (в базу не пишутся) |
| `buildings` | object \| null | Каталог построек (в базу не пишется) |
| `rods` | object | Рода по имени: `rods['Волковы']` |
| `globalResults` | object | Итоги глобальных событий: `{eventId: {majorityKey}}` |
| `auctions` | object | Состояние торгов по id события |
| `national` | object | `{stability, centralization}`, по умолчанию 10/10 |
| `releasedAssemblies` | object | Открытые ведущим ворота соборов |
| `majorityBonusResolved` | object | Метки подсчёта большинства обычных событий |
| `nationalEffects` | object | Служебные метки «мировой эффект уже применён» |
| `nationalEffects/<id>` | true | Защита от повторного применения `nationalEffect` / `nationalSet` |

### 4.2 Объект рода (`makeRod` + `patchRod`)

| Поле | Тип | Смысл |

| `answers` | object | Ответы на обычные события: `{eventId: {choiceKey, outcome, druzhina}}` |
| `votes` | object | Голоса на глобальных событиях: `{eventId: choiceKey}` |
| `flags` | object | Сюжетные флаги (`oprichnik`, `zemets` и т. п.) |
| `incomeMods` | object | Прибавки к доходу: `{key: {amount, until?}}` |
| `casualtyReduction` | number | Накопленное снижение военных потерь (доля) |
| `seenMilestones` | object | Выданные пороги знатности |
| `seenArrivalBonus` | object | Показанные бонусы по прибытии |
| `seenRumors` | object | Просмотренные слухи |
| `seenReveal` | object | Просмотренные итоги глобальных событий |
| `seenIntro` | boolean | Резерв (в текущем контенте не используется) |
| `titles` | object | Титулы, полученные на торгах |
| `favor` | object | Резерв (в текущем контенте не используется) |
| `buildings` | object | Построенные здания: `{buildingId: count}` |
| `buildWindows` | object | Решённые окна построек: `{eventId: 'bought' \| 'skipped'}` |
| `order` | number | Порядок создания рода (резерв) |

`patchRod()` вызывается при каждой загрузке снимка и восстанавливает отсутствующие
поля. Это защита от того, что Firebase удаляет пустые объекты.

### 4.3 Пути записи в Firebase

```
buntash-state
├─ currentIndex
├─ national
├─ releasedAssemblies/<eventId>
├─ globalResults/<eventId>
├─ majorityBonusResolved/<eventId>
├─ nationalEffects/<eventId>
├─ auctions/<eventId>/{round, bids, tiedRods, winner, narrative}
└─ rods/<Имя>
   ├─ resources, estate, progress, flags, answers, votes
   ├─ incomeMods/<key>, casualtyReduction
   ├─ seenMilestones/<threshold>, seenArrivalBonus/<key>
   ├─ seenRumors/<eventId>, seenReveal/<eventId>
   ├─ titles/<titleKey>, buildings/<buildingId>, buildWindows/<eventId>
```

Все записи выполняются через `dbSet`, `dbUpdate`, `dbTx`, `dbClaim`,
`txResources`, `txNational`, `setNational`. Транзакция отменяется, если функция
вернула `undefined`; `null` удаляет узел.

### 4.4 Инварианты данных

- Ресурсные ключи эффектов: только `slava`, `krestyane`, `zoloto`.
- Спецключи эффектов: `bribe`, `income`, `incomeEnd`, `casualtyReduction`.
  В ресурсы они не попадают и игроку как «+N» не показываются.
- `krestyane` после любого эффекта не ниже 20.
- Числа в эффектах — целые. Дробные допустимы только в `deploy`, `casualties`,
  `casualtyReduction`.
- `national.stability` и `national.centralization` — целые числа.
- События с `hidden: true` отсекаются при загрузке и не видны никому.

## 5. Игровой цикл

1. Ведущий создаёт рода списком: «Имя, боярский» / «Имя, дворянский».
2. Игрок открывает сайт, выбирает свой род.
3. На каждом событии род читает текст, выбирает вариант (или просто жмёт «Далее →»
   на хронике), видит исход и предварительный расчёт «Хозяйство за ход».
4. При переходе к следующему событию применяются: эффект хроники (если это
   хроника), тик экономики, награды за пороги знатности.
5. На ходах 2, 12, 22, 32, 42, 52 перед событием открывается окно «Усадьба:
   что построить». Можно купить одно здание или пропустить окно.
6. Перед соборами (assembly) род упирается в «ворота»: дальше не пройти, пока
   ведущий не нажмёт «Открыть следующий раунд».
7. На финальном соборе показываются итоговый рейтинг и вердикт державы; дополнительно —
   итоги по родам (рекорды: крестьяне, деньги, постройки, боевые холопы, централизация, стабильность).

Рода идут по событиям независимо: `rod.progress` у каждого свой. Ведущий видит,
кто отстаёт, и может открыть ворота, когда все дошли.

## 6. Механика и формулы

### 6.1 Ресурсы

| Ресурс | Ключ | Смысл | Старт |
|---|---|---|---|
| Знатность | `slava` | Очки победы, репутация рода | 14 у бояр, 10 у дворян |
| Рубли | `zoloto` | Ставки на торгах, посулы, постройки | 100 |
| Крестьяне | `krestyane` | Доход и военная сила | 200 |

«Боевые холопы» — производная величина: `floor(krestyane / 20)`, на старте 10.
Отдельным ресурсом не хранятся.

### 6.2 Тик экономики (каждый ход, кроме соборов)

Вызывается при уходе рода с события, одной транзакцией с эффектом хроники.

```
доход       = ceil(крестьяне × 0.1 + сумма активных прибавок)
бегство, %  = max(0, бегствоСтабильность + бегствоЦентрализация − бонус построек)
прирост, %  = 1 у бояр при плохой централизации, иначе 0
изменение   = roundHalfUp(крестьяне × (прирост − бегство) / 100)
крестьяне'  = max(20, крестьяне + изменение)
рубли'      = рубли + доход − расходы на снаряжение войска
```

Стабильность (ТЗ 23, одинаково у дворян и бояр): `≥ 7` — 0%, `4–6` — 1,5%, `≤ 3` — 3%.
Централизация: `≥ 5` — хорошая, 0% у обоих сословий; `< 5` — плохая: дворяне
дополнительно теряют 1%, а у бояр, наоборот, приходят +1% крестьян
(как будто бегут от дворян к боярам). Процент бегства не бывает ниже нуля,
но прирост у бояр учитывается отдельно и может дать реальный рост душ.
`fleeReduction` построек вычитается только из бегства: дешёвые здания порядка
дают по 0,5, дорогое — 1 (все вместе удерживают 2 п. п.).

Пример: плохие стабильность и централизация — дворянин теряет `3 + 1 = 4%`,
боярин «теряет» `3 − 1 = 2%`. С всеми постройками дворянин теряет 2%,
боярин не теряет ничего.

Снаряжение (ТЗ 23): дружина — `floor(крестьяне / 20)`, за каждого выставленного
холопа платится 5 рублей. Расход входит в эффект выбора и отдельной графой
«Расходы на снаряжение войска» показывается в «Хозяйстве за ход». Вариант,
который дороже доступной казны, не нажимается.

Прибавки к доходу (`incomeMods`) действуют на тиках, где `turn ≤ until`
(если `until` задан). Ключ `building:<id>` — от постройки, без срока.
Ключи из событий задаются полем `income.key`; `incomeEnd` снимает прибавку
до тика этого же хода.

«Хозяйство за ход» на экране рода считается той же чистой функцией
`computeEconomyTick()`, что и реальный тик, поэтому цифры совпадают.

### 6.3 Пороги знатности

| Порог | Награда крестьянами |
|---:|---:|
| 25 | +52 |
| 50 | +47 |
| 75 | +58 |
| 200 | +45 |
| 500 | +55 |

Каждый порог выдаётся один раз; метка ставится транзакцией
`seenMilestones/<threshold>`.

### 6.4 Разрешение эффекта выбора

`resolveEffect(source, rod, druzhina)` складывает:

1. `source.effect` — общий эффект;
2. `source.effectByEstate[rod.estate]` — сословный эффект;
3. `source.druzhinaTiers` — ступень по числу холопов (резерв, в контенте не используется);
4. все подходящие `conditionalEffects` — по флагу, сословию или минимальной знатности.

Значения по одинаковым ключам суммируются. Военные эффекты (`military.scale`,
потери), посул (`bribe`) и прибавка к доходу (`income`) добавляются в момент
клика отдельно, но входят в тот же итоговый объект.

Исход фиксируется в `answers/<eventId>/outcome` в момент выбора: тексты и готовые
числа, посчитанные по ресурсам **до** выбора. Поэтому возврат на экран позже не
пересчитывает эффект по изменившимся ресурсам.

### 6.5 Сословия

| Правило | Бояре | Дворяне |
|---|---:|---:|
| Стартовая знатность | 14 | 10 |
| При централизации < 5 | +1% крестьян (перебегают от дворян) | −1% (бегство) |
| Сословные бонусы в событиях | по данным `effectByEstate` | по данным `effectByEstate` |
| Финальные бонусы за верный выбор | — | +2 / +2 / +3 (события 53, 54, 59) |

Разница стартов и бегства компенсируется сословными эффектами и финальными
бонусами дворян. Целевой баланс: при идеальной игре максимальная знатность
одинакова у обоих сословий.

### 6.6 Военный расчёт

```
дружина   = floor(крестьяне / 20)
выставлено = roundHalfUp(дружина × deploy)
не выставлено = дружина − выставлено
потери = lossFixed  (фиксированное число)
       | min(выставлено, max(1, roundHalfUp(выставлено × casualties × factor)))
factor = max(0, 1 − casualtyReduction)
крестьяне' = max(20, крестьяне − потери)
```

`military.scale` — шкала: для каждой записи `{by, every, effect}` считается
`floor(units[by] / every)` полных групп и умножается на эффект.
`by`: `fielded` (выставлено), `missing` (не выставлено), `due` (вся дружина),
`extra` (`floor(крестьяне / 40)`).

`casualtyReduction` накапливается от выборов и снижает будущие потери.
`lossFixed` используется для формулировок «потерять ровно 1 холопа».
Снаряжение выставленных холопов стоит 5 рублей за каждого (`militaryEquipmentCost`),
но платим только начиная со второго хода; на первом ходе расхода нет.

### 6.7 Посул

```
стоимость = max(50, база − 5 × знатностьДоВыбора)
```

Списывается из рублей в момент выбора. База задаётся полем `effect.bribe`.

### 6.8 Национальные показатели

- Старт (ТЗ 23): стабильность 8, централизация 6.
- `nationalEffect` — прибавка (может быть отрицательной), применяется один раз
  на всю игру по метке `nationalEffects/<eventId>`.
- `nationalSet` — абсолютная установка значений, применяется один раз при уходе
  с события и перекрывает накопленные прибавки:
  - опричнина (`oprich-16`, ход 16): `{stability: 5, centralization: 10}`;
  - смерть Ивана Грозного (`ign-23`, ход 23): `{stability: 3, centralization: 3}`.
- Обычные события применяют мировой эффект через `majorityBonus` того варианта,
  который набрал большинство.
- Хроники (`narrative`) применяют `nationalEffect` при уходе с события,
  до тика экономики этого хода.

`worldVerdict()` на финале: централизация > 10 — сильная власть, < 5 — вольница,
стабильность < 5 — бунты.

### 6.9 Блоки и таймер

Игра делится на три блока: события 1–26, 27–44 и 45–64 (индексы 0–25, 26–43, 44–63).
В шапке экрана рода показывается «Блок N из 3» и обратный отсчёт 40 минут.
Отсчёт начинается с первого хода блока: метка времени пишется один раз
в `rods/<род>/actStarts/<блок>` при первом уходе с события блока.

### 6.10 Большинство и глобальные события

`majorityOf()`: побеждает вариант, набравший **строго больше половины** голосов
от числа ответивших. При равенстве или отсутствии большинства мировой эффект
не применяется.

- Обычное событие: личный эффект применяется сразу при ответе; `majorityBonus`
  победившего варианта даёт только `nationalEffect`. Подсчёт запускается
  автоматически, когда ответили все рода, либо кнопкой «Подсчитать сейчас»
  (делитель — число ответивших).
- Глобальное событие: при голосовании личный эффект не применяется. После
  подсчёта каждый род получает `outcomes[majorityKey].effectByChoice[свойГолос]`
  и общий `nationalEffect`. Итог показывается баннером «Вести с Земского собора».
- Метки подсчёта ставятся транзакцией `dbClaim`, поэтому эффект применяется
  ровно один раз, даже если ведущий нажал кнопку дважды.

В текущем `events.json` глобальных событий и торгов нет, но код и интерфейс
их поддерживают.

### 6.11 Торги за титул (аукцион)

- Ставка списывается сразу в момент отправки; хранится в `auctions/<id>/bids`.
- Первый раунд — все рода; при равенстве максимума объявляется второй раунд
  только среди лидеров. Побеждает единственная максимальная ставка.
- Победитель получает титул в `rods/<Имя>/titles/<titleKey>`.
- Если никто не поставил, раунд повторяется.
- В текущем контенте торгов нет.

### 6.12 Соборы и ворота

`assembly` — не игровой ход: нет выбора, нет тика, нет наград.
Род стоит на экране собора, пока ведущий не откроет ворота
(`releasedAssemblies/<id> = true`). Финальный собор (`final: true`) не
покидается: игра завершается показом итогов.

### 6.13 Финал

`finalRanking()` сортирует рода: знатность по убыванию, затем крестьяне
по убыванию, затем **рублям (zoloto) по убыванию**, затем имени по алфавиту.

Ведущий видит на финальном соборе:
- **Итоговый рейтинг родов** (`finalRanking`, новая сортировка);
- **Вердикт державы** по национальным показателям (сильная центральная власть / боярская вольница / смута и бунты);
- **Итоги по родам** (новая система оценки): род с наибольшим количеством крестьян,
  род с наибольшим количеством денег, род, построивший максимум зданий, род,
  отправивший наибольшее число боевых холопов в игру, род, давший максимальную
  централизацию, род, давший максимальную стабильность.

Вердикт державы считается по национальным показателям. Род на финальном соборе видит финальный текст.

В одном окне можно купить ровно одно здание или пропустить окно.

### 8.3 Покупка

`buyBuilding()` — одна атомарная транзакция по узлу рода. Проверки:

1. окно ещё не решено;
2. количество зданий меньше `maxCount` (если ограничение задано);
3. рублей хватает на цену.

При успехе: списывается цена, применяется `onBuild` (знатность/крестьяне/рубли,
пол душ ≥ 20), здание записывается в `buildings`, окно — `'bought'`,
а при наличии `perTurn.income` создаётся `incomeMods['building:<id>']` без срока.
При любой неудаче не списывается ничего.

`perTurn.fleeReduction` суммируется по всем построенным зданиям и вычитается из
процента бегства (итог не ниже 0): дешёвые здания порядка 0,5, дорогое — 1.
`perTurn.income` входит в тик дохода.

- Кнопка-плашка «Усадьба» с числом построек — третья в ряду национальных плашек.
- Окно «Ваша усадьба: что построить»: казна, 4 категории, карточки с картинками,
  цена, бонусы, состояния «Построить / Не хватает N руб. / Построено / Выбор сделан».
- Подтверждение покупки, экран результата, детальная карточка (Esc закрывает).
- Экран «Ваша усадьба»: сетка построенного, пустые места — силуэты.
- Картинки: `assets/buildings/<id>.png`, 512×512; при ошибке загрузки —
  плитка с emoji (`onerror` добавляет класс `missing`).
- Технические поля (`balanceTodo`, `id`, `null`) в интерфейс не выводятся.

## 9. Интерфейс и тексты

### 9.1 Экраны рода

1. **Лендинг** — герб «Б», название, подзаголовок «Ролевая игра для 7х классов»,
   кнопка «Начать игру», мелкая ссылка «вход для организатора», подпись школы.
2. **Выбор рода** — список чипов «Имя · боярский/дворянский», «← назад».
3. **Ход**:
   - шапка: сословие и имя рода, титулы, таймер блока 40 минут, кнопка «перейти к выбору рода»;
   - верхний ряд: Знатность, Рубли, Крестьяне, Боевые холопы;
   - второй ряд: Централизация, Стабильность державы, Усадьба;
   - плашки эпохи и типа события, заголовок, описание;
   - кнопки вариантов или исход выбора, дельты ресурсов, военные потери;
     варианты, которых игрок не может оплатить, неактивны;
   - блок «Хозяйство за ход» (включая «Расходы на снаряжение войска») и кнопка «Далее →»;
   - «История ▼» — пройденные события и выбранные варианты;
   - слухи, итоги глобальных событий, бонусы по прибытии — отдельными карточками.
4. **Постройки** — см. раздел 8.4.
5. **Финал** — «Игра завершена», итоговый текст.

### 9.2 Экраны ведущего

- Таблица родов с сортировкой по знатности / крестьянам / рублям.
- Таймлайн всех событий с прогрессом «N из M» и переходом к событию.
- Блок «Ворота»: сколько команд дошли, кнопка открытия следующего раунда.
- Создание родов списком, удаление нетронутых родов.
- «Темп»: отстающие сверху, прогресс-бар.
- «Ожидают подсчёта»: «Подсчитать сейчас».
- Рассадка на соборах: по знатности, затем крестьянам, затем имени.
- Ручная корректировка ресурсов, итоги торгов, финальный рейтинг и вердикт.
- Переключение текущего события (`currentIndex`) для показа нужного хода.

### 9.3 Оформление

Палитра в `:root`: тёмное дерево (`#231B14`), пергамент (`#EFE3C8`), сургучная
печать (`#8C2A20`), золото (`#B8912E`), зелёный (`#3F5741`). Основной шрифт —
Georgia / Palatino / Times (serif), интерфейсные подписи — Segoe UI / Arial.
Максимальная ширина `#app` — 1100 px. Вёрстка адаптируется под планшеты
и телефоны; на широких экранах карточки построек раскладываются в несколько
колонок.

### 9.4 Правила текстов для интерфейса

- Только человеческие формулировки: «Знатность +3», «Крестьяне: −6», «Рубли: +170».
- Никаких технических слов: `null`, `TODO`, `balanceTodo`, внутренних id,
  названий функций и формул.
- Бегство показывается без процентов: строка-причина, затем фактическая потеря
  крестьян («Крестьяне: −6»), затем доход («Рубли: +170»).
- Доход от событий: «Увеличение дохода: +N в ход» / «Уменьшение дохода: −N в ход».

## 10. Ведущий: сценарий партии

1. Создать рода (список «Имя, сословие»).
2. Открыть первый собор, когда все подключились.
3. Следить за темпом; открывать ворота, когда все дошли.
4. На соборах показывать рассадку.
5. Подсчитывать большинство, если автоматика не сработала (нужен открытый
   интерфейс ведущего).
6. На финале показать рейтинг, вердикт и итоги по родам (рекорды).

| `node tools/simulate.js` | Прогоняет стратегии по событиям, пишет CSV |
| `node tools/simulate.js --seed 7` | Другой seed для случайной стратегии |
| `node --check <file>.js` | Синтаксис любого файла |
| Открыть `index.html` через сервер | Проверка в браузере |

Линтер проверяет: 64 записи, индексы соборов `[0, 26, 44, 63]`, диапазоны ходов,
типы (57 normal / 3 narrative / 4 assembly), уникальность id, минимум 2 варианта
у normal, отсутствие вариантов у narrative, запрещённые шаблоны текста, флаги,
`nationalEffect` (целые числа, только stability/centralization), `military`
(deploy/casualties в [0,1], допустимые `by`), ключи и целостность эффектов.

`tools/simulate.js` читает правила из `state.js` через `loadRules`, поэтому
симуляция использует те же формулы, что и игра. Стратегии: максимум золота,
максимум знатности, минимум потерь крестьян, случайная.

## 12. Известные ограничения и расхождения

1. **`tools/simulate.js` дважды учитывает `conditionalEffects`.** `resolveEffect`
   уже включает условные ветки, а симулятор добавляет `findConditionalEffect`
   ещё раз. Цифры в отчётах симулятора завышены. Временный скрипт оценки
   максимумов (`max_resources.js`, вне репозитория) это уже исправляет.
2. **Автоподсчёт большинства требует открытого интерфейса ведущего.** Подписка
   вызывает `resolveMajorityBonus` / `resolveGlobalEvent` только при `role === 'gm'`.
3. **Роль и выбранный род не сохраняются.** Перезагрузка страницы возвращает
   на лендинг.
4. **`config.picksPerWindow` и `windowTurns` не читаются кодом.** Расписание окон
   задаётся флагами `buildWindow` в `events.json`, лимит — через `buildWindows`.
5. **Глобальные события и аукционы не используются в текущем контенте**, хотя
   механика и интерфейс готовы.
6. **Нет автотестов в репозитории.** Проверки — скрипты и ручные сценарии;
   часть временных скриптов не коммитится.
7. **Нет правил безопасности Firebase.** База открыта на запись.
8. **Изображения построек тяжёлые** (≈300–700 КБ каждое): на слабом интернете
   возможна заметная задержка; предусмотрен fallback на emoji.
9. **Полная перерисовка DOM** на каждое изменение — простота важнее
   производительности; при большом числе родов возможны задержки.

## 13. Баланс: базовые ориентиры

Оценка максимумов при идеальной игре (beam search, без аукционов, исходы
глобальных событий в пользу рода):

| Показатель | Бояре | Дворяне |
|---|---:|---:|
| Максимум золота | ≈ 9 109 | ≈ 9 135 |
| Максимум знатности | 823 | 823 |
| Крестьяне при максимуме знатности | ≈ 588 | ≈ 582 |

Максимум знатности выровнен: дворяне получают +2 / +2 / +3 знатности за верный
выбор в событиях `per-53`, `shved-54`, `turk-59`. При неверных выборах бонуса нет.

Максимум золота достигается покупкой доходных зданий (приказная изба, маслобойня,
железный завод, суконные фабрички); максимум знатности — покупкой влияния
(ворота, церковь, хоромы, псарни) и двух вотчин.

## 15. Журнал ключевых решений
